# supernote-hardcover

Supernote plugin that sends the reading position of the EPUB or PDF open in DOC to Hardcover (hardcover.app). The account is signed in on the device (OAuth device grant, see "Sign-in"); the package holds only a public client id. Workspace-wide rules are in `../../CLAUDE.md`; SDK how-tos are in the `supernote-plugin` skill. The public docs are `README.md` (users: install, usage, troubleshooting) and `docs/developer.md` (contributors: setup, OAuth client id, build, layout, release flow); keep them in step when behaviour, the build or the release flow changes.

## How it works

`index.js` is only the entry point the build scripts bundle; `src/plugin.ts` is boot and wiring (about 70 lines). Folders, with the import direction `ui` -> `page`/`core`, `page` -> `core`/`hardcover`/`device`, `core` imports only `core`:
- `src/device/`: the only code (besides `plugin.ts`) that imports `sn-plugin-lib` or `NativeModules`: `reader.ts` (sample, selection), `permissions.ts`, `files.ts` (native module, the SQLite database, meta cache, token store), `host.ts` (dialog, close, fake-SDK check).
- `src/hardcover/`: `client.ts` (the API, its book type is `ApiBook`), `auth.ts`.
- `src/core/`: pure logic and the shared types (`types.ts`: `BookDetail`, `Edition`, `Entry`, `Review`, `ReadingItem`, `STATUSES`): epub, match, resolve, tracker, journal, quote, store, util.
- `src/page/`: what the plugin does for the page, built with injected dependencies (tests pass fakes): `meta.ts`, `library.ts` (library cache, add flow), `tracking.ts` (touch handler, tracker), `api.ts` (the functions the page calls), `detail.ts`, `session.ts`.
- `src/ui/`: the pages, `theme.tsx` (the "Quiet page" design language: colours, shared styles and the shared parts `TopBar`, `Button`, `Link`, `Tabs`, `Options`, `Pill`), `preview/` (mock data). It never imports the SDK; `session.close` and `session.isFakeSdk` are set by `plugin.ts`.

Everything except `src/plugin.ts` and `src/device/` is SDK-free and unit tested (`npx jest`, `__tests__/` mirrors `src/`). The whole plugin is TypeScript except the config files and the generated `src/clientId.generated.js`; `npx tsc --noEmit` checks it.

- Tracking is touch-driven, with no timer and no button press needed once a book is switched on: `registerMotionListener` fires on every finger-down, the plugin reads file path, page and total, and `src/core/tracker.ts` decides when to push. Tracking is per document and OFF by default: the page's toggle turns it on for the open book, and the flag is saved as `tracking` in that file's row of the metadata cache (the `files` table of the SQLite database, see the native module bullet; next to the edition; the entry is dropped when the file size changes, which resets it to off). A book that is off is ignored on touches. Turning it on or off calls `tracker.forget(path)`, so a book is never pushed on the touch right after switching it on. A lost sign-in (`SignedOutError`, or a 401 the refresh could not fix) stops all tracking until the page signs in again.
- Push rules (owner decisions; same idea as the KOReader plugin's percentage mode): never on first sight of a book; every change of the edition page is pushed (position = `(page + 1) / total`, so font size and orientation do not matter), both directions, at most one push per 10 s per book (`PUSH_INTERVAL_MS` in `src/core/tracker.ts`, checked against timestamps at touch time, no timer). A page turned inside the window stays pending (latest wins) and goes out at the first touch after it; going back to the pushed page clears it. Hardcover merges the updates into one journal entry. A page turned at the last tap is only seen at the next finger-down, so it goes out at the next touch.
- Button `Hardcover` (id 100, `showType: 1`) opens the detail page full screen (`src/ui/App.tsx` + `src/ui/DetailPage.tsx`). `onButtonPress` fires too: it samples the open document (`session.pending`) before the view covers it. plugin.ts and the page share one JS runtime, so plugin.ts hands the page its functions through `src/page/session.ts` (`session.api`: load, setStatus, setEdition, setTracking, addToLibrary, linkBook, searchBooks, pickBook, writeReview, saveReview, loadReviews, likeReview); the page never sees the SDK or the token. `load()` = sample -> `resolvePath` -> `fetchBookDetail` -> `buildDetail` (`src/page/detail.ts`). A book that is not in the library is looked up in the whole catalogue (`catalogueBook` in `src/core/resolve.ts`: ISBN first, else title + author search; there `matchBook` runs `ranked`: title words that are part of the hit's own author names do not count and a tie goes to the search rank, so "Meditations" wins over "Meditations of Marcus Aurelius". The library match keeps its tie rule). The first time, a Yes/No dialog naming title and author asks whether to add it (only from a button press, `link` / `linkFromCatalogue` in `src/page/library.ts`; a touch never opens a dialog). Yes with an ISBN edition adds it at once; Yes without one makes `load()` return `{pick}` and App shows the edition picker first (Cancel closes the view and writes nothing; a book with no edition that has pages is never linked: an automatic match falls through to the book search, a picked hit is refused with a message and Retry). The add is `addOwned` (`src/hardcover/client.ts`, always with an edition id): the edition goes on the Owned list (`markOwned`, creates no library entry), then `library.add` makes the entry, and the edition is saved as the file's edition. Hardcover cannot create an entry without a status and gives Want to Read (checked 2026-11-10); a book already in the library is never touched. When the catalogue has no automatic match, `load()` returns `{search}` and App shows the book search (`src/ui/BookSearch.tsx`, the picker's style: a field prefilled with the EPUB's title and author, hits from `session.api.searchBooks`, "No book found"); the picked hit goes through `session.api.pickBook` to the same dialog and picker. The book stays linked per file (`linked: {bookId, editionId?}` in that file's metadata cache entry, like KOReader's link; no second prompt), on No and also after an add: every load asks for the linked book's library entry (`entryFor`), so a book picked in the search is found again although its title does not match. The link outranks the library match in `load()` (#96): a file with a link never falls back to an entry that merely matches by title, so a picked book stays also while a wrong entry is in the library. When the resolved book (library entry or link) has no edition with a page count, `load()` returns `{search}` like a file with no match and the picked book becomes the link; the plugin never changes or removes the wrong entry (the reader does on hardcover.app), and `link` refuses a no-pages book also when it is in the library. Without an entry the page and journal work for it, but tracking and status need a library entry (progress and status take a `userBookId`), so the page hides them and shows an Add to library button (`session.api.addToLibrary`, owns the file's saved edition) instead. An EPUB whose title cannot be read shows "Could not read this book's title and author." (a button press reads it again; touches do not, until a restart). A line under the progress line (`sync` from `load()`) shows the last error or "Token rejected, tracking stopped", for the open file only (errors and pushes are tagged with the file path); the normal "Last sync: page N" line is gone (`syncNote` in `src/page/tracking.ts` returns only problems). The edition list also holds the editions the reader already uses (`mine` query) and hides those with no page count. The old status dialog (pause/resume, last sync, last error) is gone: the Tracking toggle on the page replaces it.
- PDFs (#16, owner decision 2026-11-12: no automatic detection, the filename is not used): `sample()` lets `.pdf` through, and `createMeta` (`src/page/meta.ts`) gives a PDF `{ids: []}` without calling the reader function, so a PDF's contents are never read, by a press or a touch. With no title and no ids nothing matches, and `load()` returns `{search: ''}`: the book search with an empty box. The reader then always picks both, book and edition; no default edition is ever chosen for a PDF. `link` (`src/page/library.ts`) saves nothing for a PDF: not in the library and Yes returns `{pick}` as for an EPUB (added with the picked edition, `addToLibrary`); already in the library, or No, returns `{pick: {..., link: true}}`, and the picked edition goes to `session.api.linkBook` -> `linkEdition`, which saves only `linked` and `edition` for the file and writes nothing to Hardcover. Cancel in either picker closes the view and saves nothing. `load()` never defaults for a PDF either: when the saved edition is missing or no longer in the book's list it returns that `{pick, link}` again. After the picks a PDF goes through the same code as an EPUB (page, tracking, journal, review). Measured on a text PDF (see "Measured on the Nomad"); a scanned PDF and tracking pushes for a PDF are not yet tried on the device. There is no way to unlink a file on the device: a wrong pick stays until the file's cache entry is dropped. The entry is in the metadata cache and is dropped when the file size changes.
- Edition per file: exactly one, the selected one; the page, the tracker, the journal and the push read only it. `load()` computes the default once (the file's ISBN edition, else the library entry's edition, else the first with pages) and saves it when nothing valid is saved, and `tracker.forget(path)`. Picking one in the page stores `{id, pages}` as `edition` inside the file's entry of the metadata cache (so it is dropped when the file size changes), and `withEdition` applies it to the reading item, so pages are computed and sent against that edition (`edition_id` on the read). Changing it calls `tracker.forget(path)`; `setEdition` rejects an edition without pages, and the page marks the pick saved only after that succeeds (a failed pick, status change or tracking toggle shows in the sync line). The picker starts on the first shown edition when the current one is hidden. The status picker writes `update_user_book(status_id)` after a confirmation dialog for anything but Currently reading (Cancel leaves the status alone; the book leaves the list the plugin works from); ids 1 want to read, 2 reading, 3 read, 5 did not finish are confirmed on the account (via `user_book_status`), 4 (Paused) is unused here and only known from third-party docs.
- Which book: `src/core/epub.ts` reads title/author/ISBNs from the EPUB with a few range reads (never the filename). `src/core/resolve.ts`: an ISBN-13 that Hardcover knows decides it (that book is either being read or not), else title + author against the books in the library (`src/core/match.ts`; with overlapping titles by one author the longer one wins, "Dune Messiah" over "Dune"). An ISBN whose book is not on the shelf falls through to the title match. The tracker resolves a book once (no timed re-check, which used to be a full library fetch every 10 minutes): switching tracking on saves `book: {bookId, userBookId, title}` next to the edition in the file's cache entry and the tracker builds its item from those; an entry from before this (tracking on, no `book`) is looked up once from the library list and saved. Each push first reads that one `user_books` row (`fetchUserBook`) for its status and its read in progress (the unfinished read with the highest id, also when a finished read logged later has a higher one), so the full library list is fetched only by a button press (`load()`), and `entryFor` asks for one book (`fetchUserBookForBook`). The KOReader rule (owner decision 2026-11-12): progress is written only when the entry is Currently Reading (2) and has a read in progress. Otherwise nothing is written and the sync line says why (`notTracked` in `src/core/types.ts`): "Set the book to Currently reading to track it" (`NOT_READING`), or for a Currently Reading entry without a read in progress (imported, or its read finished by hand) "No read in progress: set another status, then Currently reading" (`NO_READ`; whether re-sending status 2 starts a read is not checked). `src/page/api.ts` computes the line once (`note`): `load()`, `setTracking` and `setStatus` return it, a tracking problem such as a lost sign-in first. Because the plugin adds a book as Want to Read, switching Tracking on for a library book that is not Currently Reading asks "Set ... to Currently reading?" (`setTracking` in `src/page/api.ts`, Not now / Set; owner decision 2026-11-12 after Piranesi was added, tracked and nothing arrived): Set changes the status before tracking is saved (a failure leaves tracking off), Not now turns tracking on with the hint. No offer for a Currently Reading entry without a read (`NO_READ`). A failed push logs `push failed <title> <reason>`. A page turn never changes a status, never starts a read and never touches a finished read: the status picker or that offer starts one (the server does, on status 2), and `tracker.forget(path)` also drops that file's error.
- Progress = `round((page + 1) / total * edition pages)`, written against the file's edition (`saveProgress` in `src/hardcover/client.ts`, typed `operations.UpdateUserBookRead` with only `progress_pages` and `edition_id`: the update changes only the fields it is sent). Progress that reaches the end of the edition would finish the read and mark the book Read, so the last page is sent as `edition pages - 1` and a one-page edition is not pushed: a book is finished only with the status picker (`toPages`, the tracker and the page shown are unchanged). Checked live 2026-11-12 on a private test entry (deleted after): status 2 starts a read, a progress-only update keeps `started_at`, `pages - 1` leaves the read open and the status at 2. A query right after a write can still return the old row for a second or so. The tracker compares in these edition pages, not reader pages, so a font or orientation change (which changes `total`) neither stalls nor double-pushes.
- A touch makes no SDK call when no file has tracking on (the set of tracked paths is loaded from the cache once, `meta.anyTracked`) and no retry is pending; the open path is only known through `sample()`, so with a tracked book anywhere every touch still samples fully.
- Each touch reads the file path twice around the page and total and drops the sample if it changed, so a book switch cannot pair one book's path with another's page.
- Native module `HardcoverNative` (`android/app/src/main/java/com/hardcoversync/`, registered with `add(HardcoverNativePackage())` in `MainApplication.kt`): `readTextFile` ("" if missing), `deleteFile`, `stat` ({exists, size}; deliberately no mtime: the document app updates it every time a book is opened). It no longer writes: all persistent data is one SQLite database, `hardcover.db` in the plugin's private directory (no permission needed), through `react-native-sqlite-storage`. The library is vendored in `node_change/react-native-sqlite-storage` (npm 6.0.1 trimmed to `platforms/android`, 13 files, uses Android's own SQLite; taken from j-raghavan/sn-dictionary), referenced as a `file:` dependency and registered with `add(SQLitePluginPackage())` in `MainApplication.kt`. Its one patch: `openDatabase`'s `location` is honoured (absolute: `<location><name>`), where npm's Java always uses the plugin host's shared databases folder; `src/device/files.ts` passes `getPluginDirPath() + '/'`. Tables: `tokens` (one row, `id = 1`, the token set as JSON text; signing out writes `{}`) and `files` (`path` primary key, `size`, `meta` as JSON text: the EPUB metadata cache, keyed by path and valid only while the file size is unchanged, capped at 300 rows; a change writes one row with `INSERT OR REPLACE`, which gives it a new rowid, and the cap deletes the rows with the lowest rowid). Used through `src/core/store.ts` (SDK-free, behind the injected `Db` port `exec(sql, params) -> rows`, with an in-memory copy; never throws and has no timers; with no module or a failing call everything falls back to memory, so tracking never depends on it). `__tests__/core/store.test.ts` runs it against a real in-memory SQLite (`node:sqlite`, so jest needs Node 22.13 or newer). On first open `prepareDb` imports `tokens.json` and `meta-cache.json` (the files of versions up to 0.2.x) and deletes each once its rows are in the database (the tokens are read back first; existing rows win; a failed import is tried again at the next start). Spike on the Nomad 2026-11-13 (#101, throwaway plugin identity): open, write and read through the library settle in 4 to 7 ms from a touch in lifecycle state 1 (before any button press), at boot and in state 3 (after a view closed); `setImmediate`, which the library queues every statement through, fires in all of them; rows written before switching the plugin off and on are read back after; the file is `/data/user/0/com.ratta.supernote.pluginhost/files/plugins/<pluginID>/`; `PRAGMA journal_mode` is `truncate`, so there is no WAL file and no checkpoint is needed. Not measured: a kill of the host process or a reboot right after a write, and a native call that never settles (the store would wait, as it did with the JSON file). The plugin writes only there, so it needs no FILE:WRITE (removed from `PluginConfig.json`, with the unused `createSettings`); probed on the Nomad 2026-11-12 with a throwaway plugin holding only FILE:READ: the native module writes into the private dir and the file is still there after a plugin host restart, while the same write to MyStyle or Document fails with AccessDeniedException.
- Button `hardcover-select` (id 300, selection toolbar type 3, DOC, `showType: 1`; labels are not shown on the device): opens `src/ui/JournalPage.tsx`, a full "Add journal entry" page like hardcover.app's form, with Quote | Note underline tabs (opens on Quote) and Save in the bottom bar. `onButtonPress` reads the selection (`session.selection`, cleaned by `cleanQuote`) and the sample before the view covers it and sets `session.mode = 'journal'`; App then loads the book like the detail page and shows the journal page. Quote: the passage shown read-only plus optional thoughts. Note: only your text, no passage. Edition row opens the shared `src/ui/EditionPicker.tsx` (changes the file's edition, same as the detail page). Privacy per entry, default Private, not remembered. No tags, no date (the server stamps now). Saved with `saveJournal` (`src/hardcover/client.ts`); entry text and position come from `src/core/journal.ts`. Not yet tried on the device: TextInput and the keyboard in a plugin view, and `getLastSelectedText` from a type 3 press with `showType: 1`.
- Review: the Write review button (`writeReview`, needs a library entry, else "add the book to your library first") opens `src/ui/ReviewPage.tsx` like hardcover.app's edit form: star rating (tap or drag across five stars, half steps; tapping the current rating clears it), review text, spoilers and Sponsored/ARC checkboxes side by side, private notes box, Saving/Saved/Retry. The card starts from what the entry holds (`fetchReview` = `library.get`: rating, text, spoilers, notes, plus one small `graphql` query for `user_books.sponsored_review`, which the SDK's entry lacks) and saving replaces it. `saveReview` in `src/hardcover/client.ts` is one typed `operations.UpdateUserBook` (`library.update` has no sponsored flag): `review_markdown`, `review_has_spoilers`, `private_notes` (an emptied box clears them), `rating` only when set, `sponsored_review` always (so a review can be unmarked; the flag's round trip was checked live 2026-11-12); empty text refused. Inline spoiler blur, review date, URLs and reads are not implemented. Design board: "PR #56: Write review" in the design artifact. Not yet tried on the device or against the live API.
- Journal format (verified 2026-11-10 with three private test posts on the owner's account and against public entries): `insert_reading_journal` with `event` `quote` or `note`; `tags` is REQUIRED (send `[]`); a quote with thoughts is `passage + "\n\n━━━\n\n" + thoughts` in one `entry` (hardcover.app draws ━━━ as a divider, other clients write the same) and stays `event: quote`; position goes in `metadata.position = {type: "pages", value: edition page, percent, possible: edition pages}` and shows as "p. 83". `{page}` in metadata (the old guess) is wrong.

## Measured on the Nomad (firmware 3.29.x, sn-plugin-lib 0.1.65, 2026-11-09)

- **Timers vs events (the key fact):** `setTimeout`/`setInterval` run only in lifecycle state 2 (after a button press; not at boot, not after a view closed = state 3). `registerMotionListener` touch events and SDK calls (path, page, total) work in ALL states, including before any press and after a view closed. So anything that must happen later is decided from timestamps at the next touch, and a view (showType 1) can be used without stopping tracking. Unexplained: during one early probe the timer was silent for about 7 minutes with the device on the home screen or locked.
- A `showType: 1` view is full-screen: `regionType: 1` (center dialog) with `regionWidth: 720, regionHeight: 540` was ignored (layout 749x998 dp = whole window, 2026-11-09). The SDK documents regionType 0 none, 1 center dialog, 2 fullscreen, 3 fullscreen not dismissed; SuperDashboard and the dictionary plugin also get a fullscreen view.
- Gestures (tap, finger swipe, two-finger swipe are the options; measured): every gesture starts with one finger-down (action 0, tool 1) and ends with a plain up (action 1). Two-finger swipes add action 261 and 5/6 or 262 (the pointer index is in the high byte). The reader flips the page a few ms to about 1 s AFTER the up, so a read at the up is often the old page; a read at the next finger-down is always current. A touch-driven read is therefore one gesture behind: `src/core/tracker.ts` counts a page change from the PREVIOUS read.
- `showRattaDialog(tip, left, right, ok)` resolves `false` for the left button and `true` for the right (also confirmed by Ink2Task).
- `getCurrentPageNum` is 0-based. In a note the page works but `getCurrentTotalPages` errors ("not allowed"); with the screen asleep it errors ("handwriting app is not open"). With Settings in front, SDK calls hang: every call has a timeout.
- `getLastSelectedText` works on EPUBs; the text has a `\n` at every page line wrap (`src/core/quote.ts` joins them) and may start mid-word.
- PDFs (spike for #16, 2026-11-12, text PDF `BetrVG.pdf`, 47 pages): `getCurrentFilePath`, `getCurrentPageNum` (0-based) and `getCurrentTotalPages` work as in an EPUB, on a button press and on touches (`{path: .../BetrVG.pdf, page: 28, total: 47}`). The selection toolbar button appears and `getLastSelectedText` returns the text (31 characters, starting and ending mid-word). Pen annotations go to `BetrVG.pdf.mark` next to the file (it grew from 340844 to 677432 bytes) and the PDF itself kept its size (276299 bytes), so the size-keyed cache entry survives annotating. Typing in the book search's empty TextInput works with the on-screen keyboard: search, add dialog, edition picker and the book page ran end to end ("Page 447 of 724" for page 29 of 47). Not measured: a scanned (image-only) PDF, and a PDF larger than a few hundred KB.
- `fetch('file://...')` works with FILE:READ, ignores `Range`. `fetch -> blob() -> blob.slice() -> FileReader` reads only the slice into JS: about 70 KB and 0.4 s per book instead of 5 s for the whole file.
- No JS file write exists in the SDK, React Native or the host (no fs library), hence the native module above. Verified on the Nomad 2026-11-09: write, read-back and stat round trip in the private dir; settings.json created in MyStyle after the FILE:WRITE grant; after a plugin restart (Settings > Apps > Plugins > the ON switch off and on) the first touch logs "metadata from the saved cache" 61 ms after the touch instead of a 350-500 ms EPUB read.
- File write from JS only (spike 2026-11-12, run on the Nomad with a FILE:READ-only probe plugin): `fetch` PUT and POST to `file://` fail ("Network request failed"), `XMLHttpRequest` PUT fails, and `sn-plugin-lib`'s `FileUtils` has exists, makeDir, rename, copy, list, md5, delete and no content write (`copyFile` from the private dir to MyStyle never returned). So the native module stays.
- `adb shell input tap` does NOT reach the plugin's touch listener; only real touches do, so tracking cannot be driven or tested with injected taps.
- Hardcover: a progress update creates one public `progress_updated` journal entry, and later updates merge into it: 17 s apart, and also an update 71 minutes later the same day updated the same entry in place (window longer than that, probably the day). Account default privacy is Public. ISBNs differ between files and the user's chosen editions, and file metadata can hold typo ISBNs (Circe), so ISBN and title/author are both needed.

## Sign-in (OAuth device grant, RFC 8628)

No token ships in the package. `src/plugin.ts` builds an `OAuthSession` (`@hardcover/sdk/oauth`, public client id from the `HARDCOVER_OAUTH_CLIENT_ID` environment variable, else a `.env` in the repo root, via `scripts/write-client-id.js`, no secret) and passes it to every call in `src/hardcover/client.ts` as the client's `auth`: the session refreshes before expiry on the next call (no timer, so it works in every lifecycle state), replays a 401 once, runs one refresh at a time and stores the rotated refresh token. Tokens live in the one row of the `tokens` table of the SQLite database in the plugin's private dir (`fileTokenStore` in `src/hardcover/auth.ts` over a `JsonFile` on `tokenSlot`, see the native module bullet; written with `strict` so a failed write rejects instead of leaving a stale refresh token; without the database they are memory only and a restart signs out). A `tokens.json` from an older version is imported on the first start, so updating keeps the sign-in. Scopes (`SCOPES` in `src/hardcover/auth.ts`): read:me:content, read:library, write:library, read:catalog, write:reviews (review card), read:social (other people's reviews), write:social (liking a review), read:journal (read-back of a journal add; without it the entry posts but the call fails), taken from the SDK's per-call docs. Sign-ins stored before write:reviews / read:journal / write:social were added lack them: `writeReview`, `saveJournal` and `likeReview` check `oauth.tokens().scope` (`hasScope`) and, if missing, asks in a dialog, signs out and reloads to the Sign in button. `load()` also compares the stored grant with `SCOPES` and, once per session, offers a new sign-in when any scope is missing (cancel keeps going; `ensureScope` in `src/page/api.ts` still asks per feature). A sign-in lost for good (failed refresh, revoked app, 401) turns tracking off through `signInLost` in `src/page/tracking.ts` and shows a one-time dialog, also from a touch. A button press with no stored tokens shows "Sign in to Hardcover" with a Sign in button (`session.api.signIn`): the page shows the verification URL, the code and a QR code of `verification_uri_complete` (`src/ui/QrCode.tsx`, `qrcode-generator`, pure JS drawn with Views, no native code) while the SDK polls (timers run after a button press), then reloads. Pressing the button again (a reload) aborts the waiting attempt (`signInAbort` in `src/page/api.ts`), so the Sign in button comes back. The pending sample and the selection are kept through the sign-in (load checks it first), and a successful sign-in calls `tracker.reset()` (cached items hold the old account's ids, the last error is cleared). The old personal token (`HARDCOVER_KEY`, `write-token.js`) is gone with no fallback: the first run after updating asks for a sign-in. Not yet tried on the device: the real scopes list against the account's client, and the refresh path (needs an access token to expire).

## Hardcover client

`src/hardcover/client.ts` is the only file that talks to Hardcover, through `@hardcover/sdk` (pinned 0.1.1, ESM only, jest transforms it). Library, book/edition reads, status and quotes use its resources (`library.list`, `books.get/editions/edition/findByIsbn`, `library.setStatus`, `journal.add`); the progress write uses the typed `operations.UpdateUserBookRead` because `reads.setProgress` takes no edition. It follows the documented read lifecycle (workspace `docs/hardcover-api/guides/updatingabooksprogress.md`): no read is ever inserted and no dates are sent. The client is created with `pace: false` (the SDK would wait with `setTimeout`, which only runs in lifecycle state 2) and `maxRetries: 0` (the tracker owns retries). SDK errors carry `status`. Known loss from the old raw queries: the detail page does not show a reviews count (`Book` has no such field). Status ids come from the SDK's `UserBookStatus` (Paused = 4 is defined there).

## Build and install

```powershell
Remove-Item Env:NoDefaultCurrentDirectoryInExePath   # this machine sets it to 1, so cmd cannot run gradlew.bat from the current folder; clearing it affects only this PowerShell process
npm run build          # writes src/clientId.generated.js from HARDCOVER_OAUTH_CLIENT_ID (environment, else ./.env), then scripts/buildPlugin.ps1 (Gradle: JDK 17, platform 35, build-tools 35.0.0, NDK 27.1.12297006, Gradle 8.13 via the wrapper)
```

Push from Git Bash with `MSYS_NO_PATHCONV=1` (it rewrites `/storage/...` paths), or from PowerShell: `adb -s SN078E10048537 push build\outputs\supernote-hardcover.snplg /storage/emulated/0/MyStyle/supernote-hardcover.snplg`. The first native build took 46 s here (Gradle was cached); the package is about 7 MB (a 6.9 MB `app.npk` plus the 1.1 MB bundle).

Install with Settings > Apps > Plugins > Select Plugin Package (not "reinstall"). Feature PRs target `dev` (squash-merged, conventional title). ## Review likes

Each review in the Reviews tab and in the full-review overlay has a like control at the right of its head line (`Like` in `src/ui/DetailPage.tsx`): `♡ N` when not liked, bold `♥ N` when liked (U+2665 followed by U+FE0E), 48 dp tap target, off while a tap is in flight. `fetchReviews` asks for `likes_count` and `likes(where: {user_id: {_eq: $me}}, limit: 1)` (one extra `me { id }` request per page; both fields checked read-only against the live API 2026-11-12). A tap sends the opposite state through `session.api.likeReview` -> `setLike` in `src/hardcover/client.ts`: `operations.Like` / `operations.Unlike` (`upsert_like` / `delete_like`) with `LikeableType.Review` ("UserBook") and the review's `user_books` id. The SDK's `likes.like` / `unlike` are not used because they turn an empty answer into a count of 0; `setLike` throws instead. The page puts the returned count into both `rv.items` and `openReview`; a failure changes nothing and shows nothing. Needs `write:social` (`ensureScope`, then a reload to Sign in), which must also be allowed on the OAuth client on hardcover.app. Smoke test 2026-11-12 with the same two operations on the owner's own library entry (the account has no review, so an entry without one, owner's choice; it ended as it started): like returned count 1, a second like returned 1 again (safe to repeat, same like id), unlike returned 0 and a second unlike 0 again, and liking your own entry is allowed. A read right after the like still showed the old count and no like for a moment, so the page uses the mutation's answer and never re-reads. Not checked: a like on an entry that has a review, and with an OAuth token (the test used a personal token). Not implemented: who liked, sorting by likes, likes on journal entries or lists. Glyphs probed on the Nomad 2026-11-12 with a throwaway JS-only plugin: ♡ U+2661 draws as a text glyph; a bare ♥ U+2665 (and ❤ U+2764) draws as a red colour emoji, larger than the text; ♥ followed by U+FE0E draws as a plain black heart. The control has no `alignSelf`, so its text sits on the baseline of name, stars and date (with `alignSelf: 'center'` it sat a few pixels low).

## Journal tab

The detail page's third tab lists the reader's own notes and quotes of the book (`session.api.loadJournal` -> `fetchJournal` in `src/hardcover/client.ts`: `reading_journals` filtered to user (`me { id }`), book and `event in (note, quote)`, newest first, 100 per request, Load more; needs `read:journal`, else the usual new-sign-in prompt). Each row has Edit (a full-screen editor over the page: the quote in large serif with its "— title · author · p. N" line, then thoughts or note text plus privacy, via `update_reading_journal`) and Remove (inline "cannot be undone" confirm with Yes, remove / Keep, `delete_reading_journal`); both need `write:library`. A quote's passage is never edited: `splitEntry`/`joinEntry` in `src/core/journal.ts` keep it as stored. The tab state resets with the page when another book loads or the journal card has been used (the page remounts). The GraphQL field names come from `docs/hardcover-api` and are NOT yet run against the live API.

## Other models

Only the **Nomad (A6 X2, getDeviceType 4)** is hardware-verified; everything under "Measured on the Nomad" is Nomad-only. A5, A6X, A5X and Manta are unverified. Sizes in `src/ui` are Nomad dp (window 749x998). `Scaled` (`src/ui/theme.tsx`, wraps `App`) scales the whole page uniformly by `window width / 749`, clamped 0.8-1.6 and exactly 1 within 2% of the Nomad, so the Nomad renders unchanged. Other aspect ratios get more layout room instead of stretching. Assumed, not measured: the Manta's window of about 1024x1365 dp (2560 px at the Nomad's density 1.875), the clamp, and the 64 dp gap in the top bar for the host's home button (position on other models unknown). Each time the view opens, App logs `[hardcover] window <w>x<h> dp, density <d>, scale <s> device type <n>`: ask testers on other models for it (`adb logcat -s ReactNativeJS`). Tests (`__tests__/ui/Scaled.test.tsx`) cover 749x998 and 1024x1365; for a visual check use an emulator with that window size in preview (`SN_FAKE_SDK=1`).
